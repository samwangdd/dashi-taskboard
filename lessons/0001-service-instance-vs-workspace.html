服务实例不是 workspace

这一课只建立一个能力：看到 Taskboard 页面或运行 taskctl 时，能准确说出请求最终由哪份代码、哪个进程和哪个数据库处理。

真实启动路径

入口npm run dev
scripts/dev.mjs
两个进程Vite 5173
API 47823
vite.config.ts
数据变化.data/taskboard.sqlite
server/app.mjs
可见结果浏览器刷新
CLI 返回 JSON

浏览器访问 5173 时，Vite 把 /api 固定代理到 TASKBOARD_PORT，默认是 47823。因此“页面来自新 checkout”并不能证明“API 也来自新 checkout”。真正决定 API 身份的是端口当前归哪个 PID。

三个容易混在一起的 workspace

Taskboard checkout

包含 server/、web/ 和自己的默认 .data。它决定启动哪版代码。

Service instance

一个正在监听的 Node PID，加上端口、数据目录和环境变量。客户端实际上只认识它的 URL。

Project workspacePath

数据库或 Codex 状态里保存的目标仓库路径。它决定 agent 应在哪个业务仓库工作，不决定 Taskboard HTTP 服务是谁。

关键后果

cd 到另一个 worktree 不会自动改写已启动服务，也不会自动改变全局 taskctl 的 URL。

你机器上的现场证据

  • 47823 当前由 PID 89134 监听。
  • 该 PID 的 cwd 是 ~/codeLab/dashi-taskboard，数据库也是这个 checkout 下的 .data/taskboard.sqlite。
  • 全局 ~/.local/bin/taskctl 却执行 ~/orca/workspaces/dashi-taskboard/main/cli/taskctl.mjs。
  • 包装器默认把请求发往共享的 http://127.0.0.1:47823。

所以这次现象不是玄学缓存：CLI 代码入口和服务代码根目录可以来自不同 checkout，而默认 URL 又让所有 workspace 汇聚到同一个端口。

为什么端口成了隐式单例锁

每个 checkout 的默认后端端口都是 47823，默认 Vite 端口都是 5173。Vite 开了 strictPort，不会自动找下一个端口。因此并行运行需要给每份 checkout 分配一对端口：

TASKBOARD_WEB_PORT=5174 TASKBOARD_PORT=47901 npm run dev

随后，CLI 也必须显式指向同一个实例：

TASKBOARD_URL=http://127.0.0.1:47901 taskctl project list

一分钟检索练习

你在 worktree B 里运行 taskctl，但没有设置 TASKBOARD_URL。端口 47823 正由 worktree A 启动的服务监听。请求会由谁处理？
